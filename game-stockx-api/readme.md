# GameStockX API

## Структура

- `auth.rs` — вход, JWT и общие функции чтения Bearer-токена.
- `collection/models.rs` — форматы запросов и ответов коллекции, wishlist и WTS.
- `collection/read.rs` — чтение списков и статистики.
- `collection/mutations.rs` — добавление, удаление и изменение цены.
- `collectors.rs` — список коллекционеров и WTS игрока.
- `product_list.rs`, `product_details.rs` — каталог и карточка игры.
- `redis.rs` — существующий пул Redis и сериализация кэша.
- `chat.rs`, `metrics_middleware.rs`, `simple_rate_limiter.rs` — чат и middleware.

Рефакторинг сохраняет SQL-запросы, маршруты, форматы ответов, тексты ошибок,
проверки доступа, TTL/ключи кэша и существующие значения метрик.
Миграции и скрипт запуска в рамках рефакторинга не изменяются.

## Проверки

```bash
cargo fmt --check
cargo clippy --locked --offline --all-targets -- -D warnings
cargo test --locked --offline
cargo build --locked --offline
```

Для `--offline` зависимости должны быть установлены заранее.

`tests/http_contract.py` сравнивает два заранее собранных бинарника API.
Нужны Docker, образы `postgres:15` и `redis:alpine`, Diesel CLI в PATH.
Скрипт создаёт отдельные временные контейнеры, применяет миграции, заполняет
тестовые данные и сравнивает 70 HTTP-ответов (статус, Content-Type и содержимое).
Рабочие базы и контейнеры не используются. Тестовые контейнеры удаляются после проверки.

```bash
python3 tests/http_contract.py /absolute/path/before-api /absolute/path/after-api
```

Проверяются авторизация, каталог и кэш, 404 карточки, коллекция/wishlist/WTS,
цены, CIB, удаление отметок и чтение чата. Тест не заменяет проверку WebSocket
и нагрузочное тестирование.

## Администраторы

Перед запуском этой версии примените миграцию
`2026-09-10-120000-0000_administrators`. Для локального запуска из каталога
с `Cargo.toml` и настроенным `DATABASE_URL`:

```sh
diesel migration run --config-file /dev/null --migration-dir migrations
cargo run --locked
```

В Docker миграция выполняется существующим entrypoint до старта API.
Нужно обновить исходники API в build context инфраструктуры и пересобрать
backend и frontend. Успешный `docker compose build` сам по себе миграции
не запускает: нужен запуск обновлённых контейнеров.

Миграция назначает администратора **только существующему** пользователю
`segasanshiro` (точное совпадение). Если такого пользователя нет, она не создаёт
аккаунт. Последующая регистрация этого имени не даёт административных прав.
Проверка после обновления:

```sql
SELECT id, user_login, is_admin FROM users WHERE is_admin ORDER BY id;
```

В профиле администратора появляется «Админка» → «Пользователи» / «Заявки».
Заявки содержат активные предложения серийников и архив принятых. Список пользователей поддерживает
поиск по части имени и серверную пагинацию. Назначение администратора требует
подтверждения; для удаления нужно ввести точное имя аккаунта.

API:

- `GET /api/profile/me` — текущие `id`, `user_login`, `is_admin`, `created_at`.
- `GET /api/admin/users?query=&limit=20&offset=0` — `{items, total_count}`;
  `limit` ограничен диапазоном 1–100, поиск регистронезависимый, `%` и `_`
  являются обычными символами, порядок стабилен по имени и ID.
- `POST /api/admin/users/{id}/promote` — назначить администратора;
  повторный запрос безопасен, возвращает пользователя с `is_admin=true`.
- `DELETE /api/admin/users/{id}` — удалить аккаунт, аватар, коллекцию,
  вишлист, WTS и сообщения в обоих направлениях; ответ `204`.

Права проверяются по БД при каждом действии. Роли не принимаются из JWT или
тела регистрации. Неверная авторизация — `401`, обычный пользователь на
админском маршруте — `403`, отсутствующий пользователь — `404`.
Удаление своего аккаунта запрещено (`409`); назначение и удаление выполняются
под общим транзакционным advisory lock, поэтому конкурирующие удаления
администраторов не могут оставить систему без админа. Все каскадные удаления
атомарны: любая ошибка откатывает операцию целиком.

### Токены и удалённые аккаунты

Эта версия заменяет прежний фиксированный ключ подписи JWT случайным 256-битным
ключом. API создаёт его один раз через системный генератор случайных чисел и
сохраняет в `auth_signing_keys`. Дополнительные переменные окружения не нужны.
Перезапуск, пересборка контейнера и несколько экземпляров API используют один
ключ из той же БД. Таблица должна входить в резервные копии; она не выдаётся API.

**После первого обновления всем пользователям нужно войти заново.**
Старые токены намеренно не поддерживаются, поскольку прежний ключ был в коде.
Новые токены содержат неизменный ID аккаунта и логин; каждый авторизованный
запрос проверяет существование этой пары. Регистрация удалённого логина не
делает старые токены действующими. Права назначенного администратора начинают
работать без нового логина; для появления вкладки в уже открытом профиле
достаточно обновить страницу.

При удалении локальный ChatServer закрывает все соединения аккаунта и обновляет
онлайн-статус. Проверка аккаунта перед отправкой и при heartbeat также защищает
чаты на других экземплярах API (закрытие неактивного соединения — до 30 секунд).

### Проверка админки

```sh
cargo build --locked
python3 tests/admin_contract.py "$(pwd)/target/debug/game-stockx-api"
```

Нужны Docker с образами `postgres:15` и `redis:alpine`, Diesel CLI и Node.js 22+.
Тест создаёт и удаляет собственные PostgreSQL/Redis контейнеры: проверяет
начальную роль, отсутствие автоматических прав при регистрации, защиту API,
поиск/пагинацию, сохранность JWT после перезапуска, атомарность удаления,
сохранность чужих данных, отключение WebSocket, повторную регистрацию логина
и конкурирующее удаление администраторов. Рабочая база не используется.

### Корона на аватаре администратора

`GET /api/users/admin-badges` — публичный список логинов администраторов для
пиксельных корон на аватарах. Эндпойнт не выдаёт ID, пароли или другие данные
аккаунтов и не предоставляет административных действий. Фронтенд использует
один общий запрос для всех аватаров и обновляет его после назначения или
удаления пользователя; изображение аватара в БД не изменяется.

## Заявки на уточнение серийников

Перед запуском применить миграцию
`2026-09-10-140000-0000_release_serial_requests` (в Docker — существующим
`migrate.sh` при старте обновлённого backend). Обновить и backend, и frontend.
В `Cargo.toml` / `Cargo.lock` добавлен декодер JPEG `image` с отключёнными
остальными форматами; новые переменные окружения и каталоги для фото не нужны.

На странице игры авторизованный пользователь может уточнить серийник релиза
PS2, PS3, PS4, PS5 или PSP (IGDB ID: 7, 9, 48, 167, 38). Модалка показывает
игру, платформу, регион и известные серийники. Нужно ввести один серийный номер,
загрузить фото коробки и подтвердить, что номер читается на предпросмотре.
Выбор из галереи телефона работает обычным файловым полем, без принудительного
переключения на камеру. Фото можно заменить до отправки.

### Фото

Фронтенд принимает фото до 15 МБ, уменьшает без обрезки и увеличения исходника,
сохраняя пропорции. Сначала пробует длинную сторону 2000 пикселей и JPEG-качество
90%, 82%, 74%, затем при необходимости 1600 и 1280 пикселей. Целевой размер —
до 700 КБ. Если этого недостаточно, просит переснять коробку крупнее вместо
дальнейшего уменьшения и потери читаемости. Canvas создаёт новый JPEG без
исходных EXIF-метаданных. Поддержка исходного HEIC/HEIF зависит от браузера;
при невозможности декодировать пользователь увидит предложение выбрать JPEG.

Предпросмотр и ссылка «Открыть крупно» используют именно подготовленный файл.
Оригинал не отправляется. Сервер проверяет, что файл — декодируемый JPEG не
больше 768 КБ, с ограничениями размера и памяти; повторного сжатия нет.
Фото хранится в `release_serial_requests.photo` (`BYTEA`) вместе с заявкой.
Просмотр требует JWT действующего администратора, ответ — `no-store`.
Фронтенд получает фото через авторизованный HttpClient и локальный blob URL:
токен никогда не помещается в ссылку изображения.

### Рассмотрение

Профиль → Админка → Заявки → «Активные» / «Архив». Обе вкладки имеют серверную
пагинацию. Карточка содержит игру и ссылку на неё, точный ID релиза, платформу,
регион, дату, автора, предлагаемый номер, **актуальные серийники из releases**
и фото, которое можно открыть крупно. Длинный список серийников свёрнут,
внутри доступны все значения. Архив также показывает дату принятия и админа.

- **Принять:** в одной транзакции заблокировать заявку и релиз, добавить серийник
  в массив `releases.serial`, записать статус `accepted`, дату и администратора.
  Старый массив сохраняется; при `NULL` создаётся массив. Повторный запрос
  принятия безопасен. Если номер уже появился после подачи заявки, дубликат
  не добавляется. Принятая заявка и фото остаются в архиве.
- **Отклонить:** после подтверждения удалить активную заявку; её фото удаляется
  вместе со строкой. Принятую заявку отклонить нельзя; её можно отдельно удалить из архива вместе с фото. Серийник при этом остаётся в релизе.
- Удаление пользователя каскадно удаляет его заявки и фото, включая архив,
  но уже принятые серийники остаются в каталоге. При удалении рассмотревшего
  админа из чужих заявок убирается ссылка на него.

Серийники нормализуются: пробелы по краям удаляются, буквы становятся заглавными.
Допускаются 3–64 ASCII-символа: латинские буквы, цифры, пробел, `- _ . /`.
Проверка дублей не учитывает регистр и пробелы по краям, но сохраняет разделители.
На один релиз и серийник допускается одна активная заявка; у пользователя —
до 20 активных заявок. Платформы проверяются сервером, роль — при каждом
админском запросе. Ошибка при принятии откатывает и серийник, и статус.
Релизы читаются напрямую из PostgreSQL, поэтому очистка Redis не требуется.

### API

- `POST /api/releases/{release_id}/serial-requests?serial=...` — JWT пользователя,
  тело — подготовленный JPEG (`Content-Type: image/jpeg`); ответ `201 {id,status}`.
- `GET /api/admin/serial-requests?status=pending&limit=10&offset=0` — активные;
  `status=accepted` — архив; ответ `{items,total_count}`, без фото в JSON.
- `GET /api/admin/serial-requests/{id}/photo` — JPEG, только админам.
- `POST /api/admin/serial-requests/{id}/accept` — принять, ответ `204`.
- `DELETE /api/admin/serial-requests/{id}` — отклонить активную, ответ `204`.

Полный цикл проверяется существующей командой `tests/admin_contract.py`:
включает JPEG, платформы, дубли, текущие серийники и регионы, закрытый доступ
к фото, архив, транзакционный откат, одновременное принятие и удаление фото.
Тестовые контейнеры изолированы от рабочей БД.


### Исправление серийника при принятии и очистка архива

Миграция `2026-09-10-150000-0000_accepted_serial` добавляет `accepted_serial`,
сохраняя исходную строку пользователя в `serial`. Существующий архив переносится
без потери данных. В Docker миграция выполняется при старте обновлённого API.

Перед подтверждением принятия администратор может отредактировать строку.
`POST /api/admin/serial-requests/{id}/accept` принимает JSON `{"serial":"CUSA-12345"}`.
Сервер нормализует и проверяет исправленный номер; в одной транзакции добавляет
его в релиз и сохраняет принятый вариант в заявке. В ответах списка `serial` —
принятое значение (для активной заявки — исходное), `submitted_serial` — исходное.
Если значения отличаются, архив показывает оба. Без поля `serial` сохраняется
прежнее поведение для старого клиента. Повтор с тем же принятым номером безопасен;
попытка принять уже обработанную заявку с другим номером возвращает `409`.

`DELETE /api/admin/serial-requests/{id}/archive` окончательно удаляет только
архивную запись и фото, сохраняя серийники в каталоге. Доступ — только админам,
в интерфейсе есть подтверждение. Обычное отклонение по прежнему DELETE-маршруту
действует только на активную заявку: устаревшая кнопка не удалит запись,
которую другой администратор уже принял.


## Kudos и Kudos Challenge

За каждую принятую заявку на серийник её автор получает **10 Kudos**. Начисление
в `kudos_awards` выполняется в той же транзакции, что добавление серийника и
принятие заявки. Первичный ключ по ID заявки защищает от повторного начисления,
в том числе при одновременном принятии двумя администраторами.

Миграция `2026-09-10-160000-0000_kudos` начисляет по 10 очков за каждую уже
существующую заявку со статусом `accepted`. В Docker она выполняется при старте
обновлённого backend, а не при сборке образа. Повторное выполнение SQL не
дублирует начисления. Ранее окончательно удалённые архивные заявки восстановить
для начисления нельзя.

Удаление заявки из архива сохраняет награду. Удаление аккаунта удаляет его
награды; повторная регистрация с тем же логином не наследует старые очки.
Отклонённые и активные заявки очков не дают.

- `GET /api/kudos?login=...` — публичный счётчик `{user_login,kudos}`,
  неизвестный пользователь — `404`.
- `GET /api/kudos/challenge` — публичный массив до 100 пользователей с
  положительным счётом по убыванию Kudos; при равенстве — по логину.
- В существующем списке `/api/collectors` добавлено поле `kudos`; количество
  релизов считается прежним способом.

Фронтенд показывает очки в хедере, собственном профиле, списке и профиле
коллекционеров. В чатах очки не отображаются. Раздел `/kudos-challenge` содержит
рейтинг и переходы к коллекционерам. Видимые индивидуальные счётчики обновляются
раз в минуту, рейтинг — при открытии или нажатии «Обновить».

`tests/admin_contract.py` проверяет начисления, откат, конкурентное принятие,
перенос старого архива и повтор миграции, сохранение награды после удаления
архивной заявки, удаление аккаунта и ограничение рейтинга до 100 строк.
